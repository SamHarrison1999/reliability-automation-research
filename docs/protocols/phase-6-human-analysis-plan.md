# Phase 6 human feasibility analysis plan

**Status:** Frozen before participant data collection

**Applicable execution phase:** Phase 7 after ethics approval

## Analysis purpose

Phase 7 is a participant feasibility study.

Its purpose is to determine whether the protocol, tasks, measures,
counterbalancing and data pipeline operate as intended.

It is not a powered confirmatory experiment.

## Units

Primary record:

`participant-task`

Clustering unit:

`participant`

Each participant is planned to provide four task records.

## Primary outcomes

- diagnosis accuracy;
- recovery-decision appropriateness;
- escalation appropriateness.

Report counts and proportions by:

- human condition;
- scenario family;
- task variant; and
- counterbalance sequence where useful for feasibility assessment.

## Decision time

For interpretable timing observations report:

- n;
- median;
- first quartile;
- third quartile;
- minimum;
- maximum; and
- individual paired differences where the matching structure supports them.

Means may be reported descriptively but are not preferred over the distribution
summary for the small feasibility sample.

## Workload

For each NASA-TLX dimension report descriptive summaries by condition.

Also derive:

`raw_tlx_mean`

as the unweighted arithmetic mean of the six dimensions.

The raw mean must be labelled as an unweighted/raw implementation.

## Reliance calibration

For H-A tasks classify:

- appropriate acceptance;
- appropriate override;
- appropriate escalation;
- inappropriate acceptance;
- inappropriate rejection.

Report counts and proportions.

Correct and incorrect recommendation trials must remain separately visible.

## Understanding

Report the distribution of the 0-4 automation-understanding score and item-level
correct counts.

## Explanations

The feasibility study uses explanation coding primarily to evaluate rubric
clarity and whether participants provide interpretable rationales.

No comparative explanation-quality claim is made unless the required coding
reliability procedure has actually been completed.

## Paired descriptive contrasts

Where each participant has interpretable observations in both conditions,
participant-level differences may be reported descriptively.

Difference direction must be defined explicitly for each measure.

No p-values, null-hypothesis significance tests or statistical-significance
claims are authorised for Phase 7.

## Missing data

No imputation.

Missingness and non-interpretability remain visible with declared reason codes.

Withdrawal removes data when requested within the approved withdrawal period
and before the data have reached the declared anonymisation boundary.

## Exclusions

Participant-level exclusion requires an explicit reason.

Task-level timing can be non-interpretable without discarding the participant's
valid diagnosis/action response.

Never silently replace a failed task with an additional participant task.

## Sequence and learning checks

Feasibility analysis should inspect descriptively:

- completion rate by task position;
- timing by task position;
- error pattern by sequence;
- recommendation behaviour by correct/incorrect status; and
- participant feedback about repetition or learning.

These checks inform protocol refinement rather than causal claims.

## Stopping

The feasibility target is 8-12 participants.

Collection stops at the approved maximum unless an ethics-approved amendment
changes the sample.

The sample must not be expanded after viewing effects simply to seek a more
favourable result.

## Claim boundary

Permitted Phase 7 language includes:

- protocol feasible/not feasible;
- participants completed the task;
- observed direction;
- observed distribution;
- observed reliance pattern;
- measurement or interface problem.

Not permitted:

- statistically significant;
- automation causes;
- automation generally improves;
- representative of software engineers generally;
- production effectiveness.
